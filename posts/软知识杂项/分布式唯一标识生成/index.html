分布式 ID 诞生的缘由#

单体架构下的 ID 生成困境#

在单机系统中，数据库自增主键足以满足 ID 生成需求。然而，随着业务规模扩张到分库分表阶段，传统方案暴露出三重根本性缺陷：

  • 全局唯一性丧失：多个数据库实例各自维护独立的自增序列，分库分表后不同分片的 ID 可能重复，导致数据合并时的灾难性冲突。
  • 单点故障风险：依赖单一数据库生成 ID 时，该数据库的故障将阻断所有写入链路，形成系统性风险。
  • 性能瓶颈：数据库写入能力成为 ID 生成的硬性上限，在高并发场景（如秒杀、直播）下，ID 生成延迟可能拖垮整个业务流程。

分布式环境下 ID 的需求分析#

一个合格的分布式 ID 生成器需满足以下核心要求，不同业务场景可对优先级做差异化调整：

需求维度核心要求业务意义举例
唯一性全局绝对唯一，无任何重复 ID（最基础要求）订单 ID 重复会导致支付、物流混乱
有序性ID 最好按时间趋势递增，便于数据库索引优化、深度分页查询(自增趋势可以限定 id > ? 快速剪枝)按订单 ID 排序可快速定位近期订单
高性能单机 QPS 需支撑 10 万级以上，延迟控制在毫秒级秒杀场景每秒生成数万订单 ID 无压力
高可用无单点故障，可用性需达到 99.99% 以上位于业务核心功能，服务不可用影响公司声誉
安全性避免 ID 泄露业务敏感信息，不允许被轻易猜测防止通过订单 ID 推算平台真实交易量
可扩展性支持节点扩容，新增节点后无需重构生成逻辑扩展时能否无缝适配

主流开源技术方案的分类与核心原理#

UUID#

  • 核心原理：完全无中心依赖，在客户端本地通过随机数、时间戳、机器标识等组合生成 128 位或 96 位标识符。UUID v4 基于伪随机数生成。
  • 性能特征：单机 QPS 可达百万级以上，延迟纳秒级，无网络开销。
  • 有序性特征：完全无序（UUID v4）或仅局部时间相关（ObjectId），插入 B+ 树索引时会导致严重的页分裂，写入吞吐量下降 30% ~ 50%。
  • 适用边界：对有序性无要求、存储成本不敏感的场景，如日志追踪 ID、临时文件 ID、Session Token。

中间件生成 ID#

低并发：数据库自增 ID#

  • 核心原理：数据库自增 ID 通过单库或多库设置不同自增步长（如 3 个节点步长分别为 3，ID 为 1/4/7、2/5/8、3/6/9）实现分布式唯一。
  • 性能特征：数据库自增 QPS 约 1 万以下。
  • 优点：ID 严格有序递增，实现简单，复用现有基础设施。
  • 缺点：扩展性差（新增节点需调整步长或重新分配），存在单点瓶颈。

中等并发：Redis INCR#

  • 核心原理：利用 Redis 单线程模型和 INCR 命令的原子性，对指定 Key 进行原子自增操作。
  • 性能特征：单机 QPS 可达 5 万 ~ 10 万，延迟亚毫秒级。
  • 优点：ID 严格有序，开发运维成本低。
  • 缺点：数据相比数据库更易失，安全性降低，其 Redis 自身成为瓶颈后扩展困难。

高并发：号段模式#

  • 核心原理：以空间换频率——应用启动时从数据库批量获取一个号段（如 1 ~ 1000），缓存在本地内存中依次分配，号段耗尽时再异步获取新号段。美团 Leaf 在此基础上引入双 Buffer 机制，当前号段使用至阈值（如 90%）时，后台线程预加载下一号段，号段切换对业务请求无感知。
  • 性能特征：远程调用 QPS 可达 5 万+（美团 Leaf 官方数据，4C8G 虚拟机），TP99 控制在 1 ms 以内，数据库访问频率降低至 1/step。
  • 有序性特征：无故障时严格有序
  • 缺点：号段长度（step）需精细调优（过大浪费 ID，过小频繁请求数据库），服务重启可能丢失未用完的号段，产生号段空洞。
取号段机制#

ID 生成节点成功更新数据库记录，更新前 MaxID ~ 更新后 MaxID 之间的 ID 就是当前生成器使用的 ID 号段，只有该节点才能发放该号段内的 ID

  • 美团 Leaf-Segment：更新表并查询当前最大值是否符合自己预期，否则回滚重试

  • 滴滴 Tinyid：更新表会验证版本号是否符合预期，否则回滚重试

时间戳 + 机器位算法类（Snowflake 及其变种）#

  • 核心原理（以 Twitter Snowflake 为原型）：
    • 1 位符号位（固定 0）
    • 41 位时间戳（从自定义纪元开始的毫秒数，支持约 69 年）
    • 10 位机器 ID（可区分 1024 个节点）
    • 12 位序列号（每毫秒最多 4096 个 ID）
  • 工业界增强实现：
    • 百度 UidGenerator：引入 RingBuffer 环形缓存，异步预生成 ID 填充缓存，单机 QPS 从 100 万提升至 300 万+；支持机器 ID 持久化到数据库，节点重启时自动恢复。
    • 美团 Leaf-Snowflake：通过 ZooKeeper 持久顺序节点动态分配 WorkerID，彻底解决手动配置痛点；针对时钟回拨实现等待追平、备用 WorkerID 等多层容错策略。
  • 性能特征：纯内存计算，单机 QPS 原生可达 100 万+，增强版可达 300 万+，延迟纳秒级。
  • 优点：极致性能。

时钟回拨问题：地球自转速度不均匀（长期变慢，近年有加速迹象），导致世界时（UT1）与原子时（TAI）逐渐不同步。当两者偏差接近 ‌±0.9 秒‌ 时，国际地球自转服务组织（IERS）会宣布插入或扣除1秒。机器在运行中会不定期向时间同步服务器通信进行时间同步，系统获取到的时间存在回滚的可能性。

特殊定制#

!!! abstract 用户维度再分 微信 SeqSvr：在普通号段模式的基础上，让 User(id 的使用方) 与号段建立绑定关系，用户根据号段所属关系定向请求 ID 生成服务。

例如：20 万个用户， 前 10 万用户分配到号段 A，后 10 万用户分配到号段 B，前十万个用户发消息时，只访问 A 号段生成器。如果当前号段编号耗尽，ID 生成器则重新获取下一个号段范围(与美团、滴滴号段数据库操作类似的行为)

Tip: 当然雪花算法也可以用户维度再分，机器号与省市绑定，用户又与省市绑定，定向请求特定 ID 生成器 !!!

数字类型自增趋势 ID 混淆#

显然，数字类型自增趋势 ID 是能被外人看出业务量的，为了隐藏商业信息需要进行 ID 混淆，下面提供一个思路，类似 base64 混淆代码示例。这个方案属于重新编码，其实还是明文，更安全可以在这个基础上再搭配其他加密算法，在网关层加解密，对内部服务还是使用混淆前的数字 ID 即可。

心得感悟#

先问“要不要”，再问“怎么要”#

ID 有序性是最容易被过度设计的维度。我曾见过一个日活仅 2 万的 SaaS 产品，团队耗费两周开发了完整的 Snowflake 集群，结果发现业务根本不需要排序，直接用 UUID 即可满足。非核心业务场景下，复杂度本身就是一种负债。判断依据很简单：如果业务不需要按 ID 排序分页，也不需要通过 ID 推断创建时间，UUID 就是最稳妥的选择。

依赖成本是隐形成本#

技术选型文档往往只标注 QPS 和延迟，却很少提及运维成本。选择 Redis INCR 方案意味着团队需要维护 Redis 集群的高可用和持久化策略；选择 Leaf-Segment 需要理解双 Buffer 的调优参数和号段浪费容忍度；选择 Snowflake 则需要自建时钟监控体系。在中小团队中，优先选择与现有技术栈重叠的方案，远比追求极致性能更重要。如果公司已深度使用 Redis，INCR 方案就是最优解；如果公司已经部署 ZooKeeper 做服务发现，Leaf-Snowflake 的 WorkerID 管理成本几乎为零。

不要低估业务增长的加速度#

选型时必须考虑未来 12 ~ 18 个月的业务增长空间，预留至少 3 ~ 5 倍的性能余量。对于预期高速增长的业务，宁可初期稍显“过度设计”，也好过半年后推倒重来。

关注极端场景的容错能力#

ID 生成服务不是不能出错，而是出错后必须能快速恢复且不产生污染数据。Snowflake 的时钟回拨如果没处理好，产生的重复 ID 可能污染下游数十个系统，数据修复成本极高。号段模式的服务重启丢失一个未用完号段，在订单量级下可能造成几千个 ID 空洞，虽不致命但影响数据分析。选型时应重点审视方案的“故障隔离”能力——是静默失败还是污染扩散？能否回滚或跳过？
