Java 基础

若干个月前，在《JVM 垃圾回收摘要》中，博主根据 Oracle 的 java8 文档概述了下垃圾回收，最近才发现 Oracle 对 java8 的维护截止到 2020 年底，随后只能在依靠社区维护。

尽管目前最新的版本是 java14，但 java11 才是长期维护版本，它将持续到 2026 年底，这次就我这次就从 java11 的文档中翻翻有啥新鲜玩意儿，下列是我的主要参考资料：

OpenJDK Wiki

Oracle Standard Edition Documentation

简介#

正如大家所熟知，Java 提供了垃圾自动回收的特性，程序员不在需要在编码阶段过度关注内存施放问题，而这个特性就是有 JVM 的垃圾收集器实现的。（下方内容基于 java 11 文档)

Oracle JDK 与 Open JDK 区别#

用通俗的话来讲 Open JDK 是社区版，Oracle JDK 是商业版。 除去商业特性功能，他们之间的差别其实较小，尤其在 Java11 后， Oracle JDK 是基于 Open JDK 构建的。

你也可以把 Open JDK 比作原型机，Java 生态的摸索、演进、升级基本都在它身上实验，Oracle JDK 则是基于原型机实验结果，优化改造的成品机，更稳定、有一定新特性，而这是由 Oracle 公司进行收费的。

画外音： 并不只有 Oracle 有改造版的 JDK ，有兴趣可以自行搜索，甚至你下载 Open JDK 后也可以自行发行一版

垃圾收集器#

垃圾收集器是一种内存管理工具，它通过以下操作执行自动动态内存管理：

  • 从操作系统分配内存/将内存交还给操作系统
  • 当应用程序请求内存时，将内存分配给它
  • 确定应用程序仍在使用内存的哪些部分
  • 回收未使用的内存供应用程序重用

Java HotSpot垃圾收集器采用各种技术来提高这些操作的效率：

  • 将分代清理与老化结合使用，将精力集中在堆中最有可能包含大量可回收内存区域的区域
  • 使用多线程积极地使操作并行，或者在后台与应用程序并发地执行一些长时间运行的操作
  • 尝试通过压缩活动对象来恢复更大的连续可用内存

分类#

就好比站在不同的角度可以对同一事物进行不同的分类——人可以分为男人和女人、老人和小孩…… 坊间对垃圾收集器也有不同的分类方式，按回收对象是新生代还是老年代分、按回收算法使用的什么类型分…… 各位可以自行搜索参考。我这里结合 Open JDK、Oracle JDK 官方文档，分为下列四类：

名称备注实例
serial collector串行收集器 ；使用单个线程来执行所有垃圾收集工作，这使得它相对高效，因为线程之间没有通信开销。它最适合单处理器机器serial collector
parallel collector并行收集器(也称为吞吐量收集器);类似于串行收集器，主要的区别是多线程被用来加速垃圾收集。它适用于在多处理器或多线程硬件上运行的具有大中型数据集的应用程序parallel collector
mostly concurrent collector近乎并发收集器；程序运行同时也能执行大部分清理工作，因垃圾收集而导致的暂停时间较短。它是为具有中型到大型数据集的应用程序而设计的，其中响应时间比总吞吐量更重要，因为用于最小化暂停的技术会降低应用程序性能CMS(Concurrent Mark Sweep Collection —— 在 java 11 后被移除，不再为可选项)、G1( Garbage-First Garbage Collection )
concurrent collector并发收集器；若干重型回收工作是和应用线程并发执行的，这极大地限制了垃圾收集对应用程序响应时间的影响，事实上只有一个实例 ZGC，那我说一下其设计目标： ① GC 停顿少于 10 ms(官方给出的基准测试甚至可以比 G1 快 150 倍) ② 可处理堆大小从数百 MB 提升到更大量级(实际支持 8 MB~ 16 TB) ③ 与使用 G1 相比，吞吐量下降不超过 15% ④ 采用 着色指针(colored pointers)、读屏障(load barriers) 方案，为后续优化奠定基础 Warning：这是在正常运行的情况下，使用不当的异常情况，同样可以非常拉胯，比如 STW 数秒之久ZGC(Z Garbage Collector)

垃圾回收器的选择#

按上述的分类方式，从上到下都是一次次的时代变了，越在下面的，越是跟着硬件设备升级更新后的优化产物，大体上可以认为往新了的选没毛病。

如果需要垃圾回收的一套指导规范的话可以是：

  • 首先调整堆大小以调整性能，若仍未达到预期可以尝试使用垃圾回收器
  • 你可以尝试 -XX:+UseSerialGC，如果你的应用是非常小的数据集(不超过 100 MB)
  • 你可以尝试 -XX:+UseSeriagc，如果应用程序将在单个处理器上运行，并且没有暂停时间要求
  • 你可以尝试 -XX:+UseParallelGC，如果：
    • 应用程序性能峰值是第一优先
    • 没有暂停时间要求，或者暂停一秒钟或更长时间是可以接受的
  • 你可以尝试 -XX:+UseG1GC，如果响应时间比总吞吐量更重要，并且垃圾收集暂停时间必须保持更短
  • 你可以尝试 -XX:UseZGC，如果响应时间是高优先级的，并且/或者您正在使用一个非常大的堆

更多细节请自行查阅对应文档，寻找更多可配置参数

回收算法#

垃圾回收的主要目的是清除不再使用的死对象，自动施放内存。这里常见的术语有：

  • YGC： Young Garbage Collection，针对年轻代的垃圾清理，通常速度较快
  • FGC： Full Garbage Collection，即对整个堆的垃圾回收，包括年轻代、老年代 ……
  • STW： Stop The World，指垃圾回收过程中导致的程序阻塞，等待垃圾回收完成后继续执行程序的行为

存在引用的对象很可能会被认定为是存活对象，但也有例外。比如 A 对象引用了 B 对象，而 B 对象又引用了 A 对象，A、B 对象形成了相互环岛状循环引用。事实上 A、B 在执行过后也是死对象，所以 JVM 引入了 GC Roots概念，即： 如果一个对象与 GC Roots 没有直接或间接的引用关系，那么该对象将是垃圾回收时的目标。可以作为 GC Roots 的对象包括：静态类属性中引用的对象、常量引用的对象、虚拟机栈中引用的对象、本地方法栈中引用的对象……

Mark-Clean(标记-清除算法)#

这是最基础的垃圾回收算法，该算法会从每个 GC Roots 出发，依次标记有引用关系的对象，最后将没有被标记的对象清除。但是这种算法会带来大量的空间碎片，导致需要分配一个较大的连续空间时容易触发 FGC

画外音：CMS 收集器采用的这种算法，可以尝试设置 -XX:+UseCMSCompactAtFullCollection 强制在 FGC 后对老年代对象进行压缩和碎片整理(此过程是 STW 的)，为减少 STW 次数，可设置 -XX:CMSFullGCsBeforeCompaction=n 令执行 n 次 FGC 后，才进行碎片整理

Mark-Copy(标记-复制算法)#

现作为新生代的主流的垃圾回收算法。堆内存会划分为较大的 Eden 与多块较小的 Survivor(此例中不妨假定多块为 2 块)，每次只使用 Eden 和其中一块 Survivor 进行标记，标记完成后则把存活的对象移动到另一块空闲的 Survivor中，并清空当前使用的 Eden 和 Survivor，移动过程中对象可以被整理成连续分配在内存中的形式

画外音：G1 收集器采用的这种算法，在 Java 11 中为默认垃圾回收器。G1 收集器，把堆分割成了若干个 region 块，每个 region 包括 Eden、Survivor、Old、Humongous(专门存放老年代大对象)；ZGC 同样也是这种算法，使用了着色指针(colored pointers)、读屏障(load barriers)技术优化了标记、转移的细节
