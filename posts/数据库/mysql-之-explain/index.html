简介#

EXPLAIN 是与 SELECT、 DELETE、 INSERT、 REPLACE 和 UPDATE 语句协同使用的关键字，能为我们提供一些信息，去了解当前语句 MySQL 是如何执行的。我们经常希望调整查询语句，尽可能快的得到查询结果，而 EXPLAIN 提供的信息显然对此大有裨益

EXPLAIN 返回的属性#

EXPLAIN SELECT * FROM goods; 可能会得到以下结果

idselect_typetablepartitionstypepossible_keyskeykey_lenrefrowsfilteredExtra
1SIMPLEgoodsALL101100

id (JSON name: select_id)#

此次查询结果行记录的唯一标识(通常一行记录代表一个表)，每次查询编号都会重新分配，与表间的关系不是固定的。例如分两次查询 goods、user 表，EXPLAIN SELECT * FROM goods;、EXPLAIN SELECT * FROM user; 这两个不同的记录表在各自的查询中 id 可以均为 1

select_type (JSON name: none)#

标识执行过程中使用到的表的类型，比如标识谁是主查询谁是子查询……这个好像没啥好说的，把官方原文搬运过来

table (JSON name: table_name)#

标识执行过程中使用到的表的名称。出现临时表时，此属性通常会根据 id (JSON name: select_id) 来拼接，例如 <unionM,N>、<derivedN>、<subqueryN> (M、N 为 id (JSON name: select_id))

partitions (JSON name: partitions)#

这是 MySQL 提供的表分区功能的扩展，将同一张表里满足不同条件的记录存储在不同的文件之中。在表做过分区操作之后，此属性才会有值，标识查询的内容源于哪个分区。

type (JSON name: access_type)#

查询类型，性能由好到坏从上到下排列为：

  • system： 这是一种特例，它表示表里只有一条记录

  • const： 包含的结果集，会被后续步骤的优化器视作常量，它只会读一次，速度非常快。通常发生在使用唯一键做筛选的查询中，例如：
    SELECT * FROM tbl_name WHERE primary_key=1;
    SELECT * FROM tbl_name WHERE primary_key_part1=1 AND primary_key_part2=2;

  • eq_ref： 发生在关联查询中，且关联的字段通常是当前表的 主键、非空唯一索引，对于前面表中的每一行组合，从该表中读取一行，例如：
    SELECT * FROM ref_table,other_table WHERE ref_table.key_column_part1=other_table.column AND ref_table.key_column_part2=1;

  • ref： 发生在关联查询中，且关联的字段通常不是当前表的 主键、非空唯一索引，对于前面表中的每一行组合，从该表中能根据索引获取查询结果(发生回表行为时，不属于 ref)，例如：
    SELECT join1.a, join2.c FROM join1, join2 WHERE join1.a = join2.a; (表 join2 中存在联合索引 index(a,c) )

  • fulltext： 当前表使用到了全文索引

  • ref_or_null： 博主未能复现出来，不太理解。贴上原文：

    This join type is like ref, but with the addition that MySQL does an extra search for rows that contain NULL values. This join type optimization is used most often in resolving subqueries. In the following examples, MySQL can use a ref_or_null join to process ref_table:

  • index_merge： 博主未能复现出来，不太理解。贴上原文：

    This join type indicates that the Index Merge optimization is used. In this case, the key column in the output row contains a list of indexes used, and key_len contains a list of the longest key parts for the indexes used. For more information, see Section 8.2.1.3, “Index Merge Optimization”.

  • unique_subquery： 替换一些 ref 类型中出现了 value IN (SELECT primary_key FROM single_table WHERE some_expr) 的查询

  • index_subquery： 与 unique_subquery 类似，但涉及的字段非唯一，替换一些 ref 类型中出现了 value IN (SELECT key_column FROM single_table WHERE some_expr) 的查询

  • range： 通过索引从一定范围内筛选结果集的查询。它可以涉及 =、<>、>、>=、<、<=、IS NULL、<=>、BETWEEN、LIKE、IN()

  • index： 通过索引树扫描全部记录的查询

  • ALL： 在无索引帮助的情况下做全表扫描

possible_keys (JSON name: possible_keys)#

执行过程中可能用上的索引

key (JSON name: key)#

执行过程中实际用到的索引

key_len (JSON name: key_length)#

执行过程中实际用到的索引的大小(存储大小，单位字节)

ref (JSON name: ref)#

关联查询时，描述关联所使用的字段

rows (JSON name: rows)#

描述有多少行记录需要被扫描，对于 InnoDB 的表，这个值是个估算值

filtered (JSON name: filtered)#

通过查询条件过虑后待扫描记录的百分比，100 代表没有筛选掉任何记录，下一步骤需要对此百分比的记录做扫描，这个值越小越对后续步骤就越有利。

具体扫描数=rows∗filtered具体扫描数=rows*filtered具体扫描数=rows∗filtered

Extra (JSON name: none)#

额外的扩展信息，例如： Using temporary 代表使用了临时表
